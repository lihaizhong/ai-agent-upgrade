# 向量数据库概述

向量数据库（Vector Database）是一种专门用于存储、管理和查询高维向量数据的数据库系统。与传统关系型数据库不同，向量数据库的核心能力是近似最近邻搜索（Approximate Nearest Neighbor, ANN）。

## 为什么需要向量数据库

在自然语言处理、计算机视觉和推荐系统中，数据通常被表示为高维向量（称为嵌入或 Embedding）：

- 文本可以通过 BERT、GPT 等模型转换为 768 维或更高维的向量
- 图像可以通过 ResNet、ViT 等模型转换为 512 维或 2048 维的向量
- 用户行为可以转换为表示用户兴趣的向量

当需要查找相似内容时，传统数据库的索引（如 B-Tree）无法有效处理高维空间中的距离计算，这就是向量数据库的价值所在。

## 核心概念

### 嵌入（Embedding）

嵌入是将离散对象（如单词、句子、图像）映射到连续向量空间的过程。相似的物体在向量空间中的距离更近。

### 相似度度量

向量数据库使用多种距离度量来计算向量之间的相似度：

- **余弦相似度（Cosine Similarity）**：衡量两个向量方向的相似性，范围 [-1, 1]
- **欧氏距离（Euclidean Distance）**：衡量向量空间中的直线距离
- **点积（Dot Product）**：兼顾方向和 magnitude 的相似性
- **曼哈顿距离（Manhattan Distance）**：各维度差的绝对值之和

在文本检索场景中，余弦相似度是最常用的度量方式。

### 近似最近邻搜索（ANN）

在高维空间中进行精确最近邻搜索的计算成本极高。ANN 算法通过牺牲少量精度来换取数量级的性能提升。

主要 ANN 算法：

#### HNSW（Hierarchical Navigable Small World）

- 基于图的结构，构建多层导航图
- 查询时对数级复杂度
- 内存占用较高，但查询速度极快
- 代表：FAISS-HNSW、Milvus、Weaviate

#### IVF（Inverted File Index）

- 先对向量空间进行聚类（如 K-Means）
- 查询时只需搜索最近的几个聚类中心
- 内存效率高，适合大规模数据
- 代表：FAISS-IVF、Milvus

#### LSH（Locality Sensitive Hashing）

- 将相似向量哈希到同一个桶中
- 查询时只需比较同一桶内的向量
- 内存效率高，但精度相对较低
- 代表：Annoy、FAISS-LSH

#### 乘积量化（Product Quantization）

- 将高维向量压缩为低维表示
- 大幅减少内存占用
- 适合十亿级向量检索
- 代表：FAISS-PQ、ScaNN

## 主流向量数据库对比

### Pinecone
- **类型**：全托管云服务
- **特点**：无需管理基础设施，自动扩展，内置混合搜索
- **适用场景**：快速原型、生产环境、不想运维基础设施的团队
- **缺点**： vendor lock-in，成本较高

### Milvus / Zilliz
- **类型**：开源 / 全托管
- **特点**：分布式架构，支持十亿级向量，多种索引类型
- **适用场景**：大规模企业级应用、需要分布式部署
- **优势**：社区活跃，生态完善，支持 GPU 加速

### Weaviate
- **类型**：开源 / 云服务
- **特点**：GraphQL 接口，内置向量化模块，模块化设计
- **适用场景**：需要 GraphQL 接口、多模态检索
- **优势**：开发者体验好，支持多种向量化模型

### Qdrant
- **类型**：开源 / 云服务
- **特点**：Rust 编写，高性能，支持过滤搜索
- **适用场景**：需要高性能过滤查询、Rust 生态
- **优势**：内存效率高，支持 payload 过滤

### Chroma
- **类型**：开源
- **特点**：简单轻量，Python 原生，易于集成
- **适用场景**：快速原型、小型项目、本地开发
- **优势**：API 简洁，与 LangChain 等框架集成好

### FAISS
- **类型**：Meta 开源库
- **特点**：算法丰富，性能极致，纯索引库
- **适用场景**：需要最高性能、自定义部署
- **注意**：不是完整数据库，需要自行管理元数据和持久化

## RAG 系统中的向量数据库

在检索增强生成（RAG）系统中，向量数据库扮演着关键角色：

```
用户查询 → Embedding 模型 → 向量 → 向量数据库检索 → 相似文档 → LLM → 回答
```

### 优化建议

1. **分块策略**：文档分块大小影响检索质量，通常 200-500 字符为宜
2. **重叠设置**：相邻分块间保留一定重叠，避免信息割裂
3. **元数据过滤**：结合标签、时间、来源等元数据进行预过滤
4. **重排序（Reranking）**：使用更精确的模型对初步检索结果重新排序
5. **混合搜索**：结合关键词搜索和向量搜索，取长补短
6. **索引选择**：根据数据规模和延迟要求选择合适的索引类型

## 性能考量

选择向量数据库时需要考虑：

- **数据规模**：百万级、千万级还是十亿级
- **查询 QPS**：每秒查询量需求
- **延迟要求**：P99 延迟目标
- **召回率要求**：可接受的精度损失
- **过滤需求**：是否需要复杂的元数据过滤
- **部署方式**：本地、私有云还是公有云
- **预算**：开源免费 vs 托管服务的成本

## 未来趋势

1. **多模态向量数据库**：同时支持文本、图像、音频、视频的检索
2. **图向量混合**：结合图数据库和向量数据库的能力
3. **实时更新**：支持流式数据的高频更新
4. **成本优化**：更高效的压缩和量化技术
5. **标准化**：向量搜索协议的标准化
